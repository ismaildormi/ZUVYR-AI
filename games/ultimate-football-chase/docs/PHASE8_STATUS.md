# Phase 8 — weekly standings and monthly challenge source status

**Read-only, fail-closed client source implemented; no leaderboard or real-prize contest is live.** There is no backend run validator, Firebase deployment, admin-published standings, contest rules, prize budget, identity/eligibility review, consent/retention process or signed device test in this checkout. The Hub's Top 10 screen now offers weekly, monthly and Hall tabs. In the default build every tab correctly says **UNAVAILABLE**, not ten invented players. Monthly entry/prizes are visibly disabled. Local/guest/account Hub stages, run distance and demo Coins are **never submitted or converted to ranking points**.

## Implemented

- `ILeaderboardGateway` exposes **reads only**; the default `UnavailableLeaderboardGateway` never supplies entries. A conditional `UFC_FIREBASE` gateway reads `leaderboardViews/weekly_current`, `monthly_current` and `hall_previous` via Firestore **Source.Server** only. These fixed public documents must be written exclusively by a trusted Admin SDK publisher after genuine server-side validation; there is no Unity client write/submission method. A missing, offline, timed-out or malformed snapshot yields **UNAVAILABLE**, not an empty fabricated leaderboard or a fallback from client scores.
- `firebase/firestore.rules` allows individual public **get** for those three fixed pseudonymous views, but denies all client list/create/update/delete. The example rules still default-deny the rest and require careful merging with any existing Firebase project rules. Never publish raw Firebase UID, email, personal profile, verification videos or prize eligibility in public snapshots. A client-side schema flag is **not** proof of score authenticity: Admin-only publication, secure credentials and server validation are mandatory.
- `LeaderboardPolicy` validates version, board type, period format, state, server publication timestamp, up to **10** contiguous sorted/unique pseudonymous rows (up to **3** Hall rows), bounded points and display aliases without rich-text/newline injection. The UI displays the server-provided period and publication time, with **“not a prize decision”**. Hall is an archived ranking view only — **not proof that a displayed player won, passed review or received a prize**. `Phase8Tests.cs` tests valid/malformed/read-failure paths; authored tests have **not** been run in Unity.

## Real contest security and acceptance still required

1. Implement a server-owned game session and authoritative event/rules validation: server-issued run seed/session, bounded and ordered event stream, independent calculation of score and speed/physics plausibility, rate limits, replay detection, anomaly/manual review, and an audited immutable result ledger. A perfectly forged client event stream remains possible if the server cannot independently validate gameplay; do **not** accept submitted totals or regard the present client prototype as cheat-resistant. Client-written `hubPreviews` and PlayerPrefs must never feed prizes or rank.
2. Define the scoring formula and server-clock period boundaries. Weekly Top 10 refresh and monthly **independent** score reset must be done by backend jobs (not device clock); close the monthly period at the published deadline on the last day, freeze/archive it only after validation, and publish a properly reviewed Hall. Specify tie-breaks, disqualifications, outages/late submissions and a server announcement protocol. No fake monthly winners or automated prize payouts are present.
3. Before any cash/product prizes, obtain legal/platform compliance by jurisdiction and age, publish eligibility and official rules, select an independent auditable random process for the prize among top 50, and obtain appropriately scoped consent for any winner video. Verify top-three identity/video through a **private** channel, protect/limit retention and provide an alternative path when required by law. The PDF suggests 1st-place major prize and 2nd/3rd smaller prizes; nothing in this prototype awards them. Marketing video/share graphics must not announce winners before manual verification and clearance.
4. Import/compile Unity with Firebase SDK only after project/provider setup, run phases 1–8 Test Runner suites, deploy/review Firestore rules in a rules emulator, and test guest/offline/foreign-user reads, all attempted client writes/lists, malformed snapshots, zero rows, stale period, month boundary and account switch. Verify no local score ever appears as an official result. Unity and physical Android/iOS acceptance remain outstanding for **all** previous phases.
