## Added

- Persistent account session, sign-in/out UI in Hub, Google primary and Apple ID / Game Center iOS alternatives. The optional Firebase gateway authenticates via Firebase Auth and reads/writes only `hubPreviews/{auth.uid}`. Google obtains an ID token through an optional native plugin bridge; Apple uses Firebase's federated `apple.com` provider, Game Center uses Firebase's GameCenterAuthProvider. These flows are **unverified scaffolding** pending platform credentials, plugin/API version and physical device testing.
- Guest PlayerPrefs are separate from per-Firebase-UID SHA-256-keyed account caches. Server-only reads distinguish missing documents from offline errors. A guest import is **reserved** for one UID on the first confirmed-not-found response, then marked claimed only after a server-confirmed first save (or a subsequent confirmed server read after a timed-out write). This prevents importing the same guest into another new account during an ambiguous timeout; a failed reservation can be retried only by that same UID. Sign-out restores the local guest snapshot; unsent account changes remain in that UID's local cache. PlayerPrefs is **unencrypted** and UID hashing is only key separation, not data security; no email, OAuth token or private key is stored in this cache. A production privacy/delete-data flow, secure device storage and multi-device conflict policy still require design/verification. No guest migration is performed if the remote read fails. Offline account caches cannot overwrite remote documents until a successful server read and same-UID merge. Position/outfit use latest timestamp, stage/run counters and best distance use max, **not** addition. Treat same-UID multi-device writes as provisional last-writer-wins, not a transaction.
- `firebase/firestore.rules` limits get/write to the owner UID in a separate, small **client-written preview** collection; listing/deletion and all other collections are denied by these example rules. Never use these client-controlled values for real-money prizes, wallet, purchases, rankings, verified achievements or fraud detection. Such features require server-authoritative validation and separate rules.
- Editor tests `Phase5Tests.cs` cover per-UID isolation, merge policy, cache/queue boundary, invalid values and fail-closed builds; tests are authored **but not run**.

## Integration prerequisites (owner/project integrator)

1. Create the Firebase project for the **original** Android/iOS bundle IDs; enable Firebase Authentication (Google + Apple + Game Center providers where appropriate) and Firestore. Import compatible **Firebase Unity Auth and Firestore SDK** into this Unity project and place platform Firebase config files using the SDK's official instructions. Do not commit production credentials/private keys. Check Unity compilation and Firebase dependency resolution. The Firebase Auth/Firestore precompiled DLLs must be auto-referenced by the game's runtime assembly definition. Set scripting define **`UFC_FIREBASE`** only after SDKs are installed; until then its gateway code is excluded. `FirebaseGateways.cs` uses the Firebase Unity `Source.Server` API to verify live reads/confirmed writes; test actual SDK version semantics on-device.
2. For Google primary login, import/configure a compatible Google Sign-In for Unity plugin (or provide your own `IGoogleTokenProvider` to `GoogleTokenBridge.Provider`). The example legacy plugin bridge lives **outside** the runtime asmdef because that plugin compiles into Assembly-CSharp. Place your **OAuth Web client ID** (not a client secret) in `Assets/_Game/Resources/GoogleWebClientId.txt` and set `UFC_GOOGLE_SIGNIN` only after plugin import. Verify Android SHA fingerprints, Android/iOS OAuth redirect and build signing according to provider instructions; the Google Unity sample plugin is old, so production plugin compatibility must be reviewed before shipping. Do not include a client secret in the application.
3. On iOS enable Apple Sign In/Game Center capabilities, Firebase provider configuration and proper provisioning/profile/entitlement setup. Firebase's Apple federated flow and Game Center credential flow need **real signed iOS builds**; Editor buttons are intentionally not shown for iOS-only alternatives.
4. Review `firebase/firestore.rules` alongside the project's **existing** rules before deployment (the example has a default-deny catch-all and would block other collections if used as-is). Deploy with Firebase CLI using your own project config, and test both owner and foreign UID reads/writes in the Firestore rules emulator; rules have not been deployed or executed here. Ensure other backend domains stay separate.
