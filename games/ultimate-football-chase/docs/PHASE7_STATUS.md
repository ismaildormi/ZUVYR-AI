# Phase 7 — daily wheel and advertising source status

**Guest-only demo wheel and fail-closed ad policy implemented in source; rewarded ads, real prizes and ad SDK are NOT operational.** Unity compilation, Test Runner, Firebase integration and physical Android/iOS tests remain pending. The default app cannot claim that a rewarded video was watched. No SDK, network ad receipt, trusted wallet, server wheel authority, age/privacy consent flow or production remove-ads entitlement is installed.

## Implemented / exact design figures

- PDF section 10's eight outcome weights are implemented **exactly**: 50 Coins **25%**, 100 Coins **20%**, 1 key **20%**, 200 Coins **15%**, 3 keys **10%**, ordinary box **5%**, 10 keys **3%**, 5 Gems **2%** (sum 100%). `WheelDefinition.ResultForRoll` uses 0–99 integer boundaries; the guest demo draws uniform bytes by rejection sampling. These client-side draws are **not** suitable as real-money or account reward authority.
- Hub has an eight-slot, weighted daily wheel preview. One **guest demo** spin per **UTC day** is stored atomically with its outcome in the local practice PlayerPrefs snapshot. UTC is a **provisional day boundary**; a local clock can be changed and local storage is editable. Coin outcomes credit only **local guest demo coins** (same capped demo balance as phase 6). Key, Gem and box outcomes increment **simulated, non-spendable counters**: not runner revive keys, not premium Gems, not inventory. The last selected slot is highlighted. No guest wheel data is imported into Firebase or shared across accounts; authenticated users only see a read-only wheel preview with “account spin unavailable.” The extra-ad-spin button is visibly disabled.
- Advertising placements are defined but unavailable: free revive, additional wheel spin, extra chest, end-of-run coin doubling, and store coins. Rewarded viewing must be voluntary. `UnavailableAdGateway` cannot return a successful rewarded receipt; `UnavailableRewardVerificationGateway` cannot confirm one. Pressing a UI button **never** fakes an ad view or awards a reward. Future server must validate unique network receipts and apply account rewards atomically; no client-submitted coin/score amount should be trusted.
- Interstitial pacing is **provisionally once every 4 completed attempts** (within PDF's every 3–4 attempts), only on restart/return **between** attempts, never during running, VAR, revive or free roam. A failed/unavailable SDK response never consumes the cap. This pacing counter currently lives in memory and resets when the app restarts; production pacing/consent needs a reviewed persistence policy. `AdSession` currently has the unavailable gateway only, so **no interstitial is presented**. A verified remove-ads entitlement would suppress interstitials, not opted-in rewarded ads; no such entitlement exists in this checkout. The policy math for **50 Coins after each five verified rewarded ads in the same UTC day** is present but deliberately **does not grant** anything: this requires server event validation. Rewarded spins would be unlimited by daily count per PDF, but absent SDK and server they are disabled.
- Authored but unrun Editor tests `Phase7Tests.cs` cover all 100 wheel outcomes and boundaries, one UTC spin/day, rollback behavior, demo-only counters, fail-closed ad gateways and interstitial placement/capping.

3. Do not enable the advertised real-money rewards in this prototype.
4. Verify remove-ads purchases using trusted receipts and server entitlements; restore/refund handling before honoring them. Test no interstitial mid-run/after rewarded flow and never invent ad impressions for analytics. Current `AdSession` is intentionally **not** wired to a real SDK or ledger.
